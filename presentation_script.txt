# [SLIDE 3] PROBLEM STATEMENT                          (~2 minutes)
# ═══════════════════════════════════════════════════════════════════

So, what is customer churn?

Customer churn refers to the phenomenon where a customer stops doing
business with a company. In the telecom industry — which is the
domain of this dataset — churn happens when a subscriber cancels
their plan or switches to a competitor.

Why is this important? Because acquiring a new customer is five to
ten times more expensive than retaining an existing one. Research
shows that even a five percent reduction in churn can increase
profits by twenty-five to ninety-five percent.

So, from a business perspective, if we can predict which customers
are likely to churn BEFORE they actually do — we can take
proactive action. We can offer them discounts, better service, or
personalized outreach — and save the relationship.

That's exactly what this machine learning model does. It takes a
customer's profile data — their contract type, charges, services —
and predicts the probability that they will churn in the near future.

The output is a simple label: "Yes" if the model predicts the
customer will churn, and "No" if they're likely to stay.

# ═══════════════════════════════════════════════════════════════════
# [SLIDE 4] DATASET OVERVIEW                           (~2 minutes)
# ═══════════════════════════════════════════════════════════════════

The dataset I'm using is the classic Telco Customer Churn dataset.
It contains records for over seven thousand telecom customers.

Each record has 21 columns — 20 features and one target column
called "Churn".

The features include:

  Demographics: gender, SeniorCitizen, Partner, Dependents
  Account Info: tenure (months with company), Contract type,
                PaperlessBilling, PaymentMethod
  Services: PhoneService, InternetService, OnlineSecurity,
            OnlineBackup, TechSupport, StreamingTV, etc.
  Charges: MonthlyCharges, TotalCharges

The target column, Churn, is a binary variable — "Yes" or "No" —
indicating whether the customer left the company.

One observation I noticed immediately from exploring the data is
that customers on Month-to-month contracts have a significantly
higher churn rate compared to those on one-year or two-year
contracts. This makes intuitive sense — longer commitments mean
lower churn risk.

I also noticed that high MonthlyCharges and low tenure are strong
indicators of churn — new customers paying a lot tend to leave early
if they don't see value.

# ═══════════════════════════════════════════════════════════════════
# [SLIDE 5] DATA CLEANING & PREPROCESSING              (~3 minutes)
# ═══════════════════════════════════════════════════════════════════

Now let's talk about data cleaning and preprocessing.

The first thing I did was drop the customerID column. This is just
a unique identifier and carries no predictive value for the model.

Next, I handled the TotalCharges column. Even though TotalCharges
should be numeric, I found that some rows had blank spaces or empty
strings instead of numbers. This commonly happens when a customer
signed up very recently and hasn't been charged yet. I converted
this column to a numeric type using pandas' to_numeric function with
errors='coerce', which turns those bad values into NaN. These are
then handled by the imputer.

For the target variable — the Churn column — I mapped the string
values "Yes" and "No" to binary integers: 1 for Yes and 0 for No.
This is required for the classifier to work properly.

Now for feature preprocessing — I separated features into two
categories:

  Numerical features: SeniorCitizen, tenure, MonthlyCharges,
                      TotalCharges

  Categorical features: gender, Partner, Contract, PaymentMethod,
                        and all the service-related columns

For numerical features, I used a SimpleImputer with a mean strategy
— this fills any missing values with the column mean.

For categorical features, I used OneHotEncoder — which converts
each category into its own binary column. For example, the Contract
column which has three values — Month-to-month, One year, Two year —
gets expanded into three binary columns.

I assembled these steps into a single ColumnTransformer using
scikit-learn's Pipeline API. This is critical because the SAME
transformation that was applied during training MUST be applied at
inference time. That's why I saved it as transformer.pkl.

# ═══════════════════════════════════════════════════════════════════
# [SLIDE 6] MODEL TRAINING & EVALUATION                (~3 minutes)
# ═══════════════════════════════════════════════════════════════════

For the machine learning model, I chose a Random Forest Classifier.

Why Random Forest? A few reasons:

First — it's an ensemble method, meaning it builds multiple decision
trees and combines their predictions. This reduces overfitting
compared to a single decision tree.

Second — it handles both numerical and categorical features well.

Third — it gives us probability estimates, not just binary labels.
This means we get a "churn probability" score — for example, 0.85 —
which is much more useful to a business team than just saying
"Yes" or "No".

Fourth — it naturally handles class imbalance to some degree.
In our dataset, only about 26% of customers are churners. To further
address this, I set class_weight='balanced' in the Random Forest
parameters.

My model configuration was:
  - 200 decision trees (n_estimators=200)
  - Maximum tree depth of 10 (max_depth=10)
  - Balanced class weights
  - Random seed of 42 for reproducibility

For evaluation, I split the data 80/20 into training and test sets.
I used stratified splitting to ensure the same churn ratio in both
sets.

The model achieved a ROC-AUC score of 0.75 on the test set.
ROC-AUC is my preferred metric here because it measures how well
the model distinguishes between churners and non-churners across
all probability thresholds — not just at a single cut-off.

An AUC of 0.75 means the model is performing meaningfully better
than random guessing (which would be 0.50), and meets our
minimum acceptable production threshold.

# [SLIDE 8] CODE WALKTHROUGH — train.py                (~2 minutes)
# ═══════════════════════════════════════════════════════════════════

Let me walk through the training code quickly.

In train.py, I start by loading the CSV file with pandas.

Then I apply the exact preprocessing steps I described earlier —
drop customerID, convert TotalCharges to numeric, and encode the
target.

Then I use select_dtypes to automatically separate numerical and
categorical columns. This is a clean, dynamic approach that works
even if we add more features later.

I build the ColumnTransformer — a SimpleImputer for numbers and a
OneHotEncoder for categories. I fit this on the training data.

Then I instantiate the Random Forest model with 200 trees, max depth
10, and balanced class weights, and fit it on the transformed
training data.

After training, I evaluate on the test set and print the
classification report and ROC-AUC score.

Finally, the most important step — I use joblib.dump to serialize
and save both the transformer AND the model as pkl files inside
the app/ folder. These files are what the API uses at runtime.

# ═══════════════════════════════════════════════════════════════════
# [SLIDE 9] CODE WALKTHROUGH — app/main.py             (~2 minutes)
# ═══════════════════════════════════════════════════════════════════

Now let's look at the Flask API in app/main.py.

When the Flask app starts, it immediately loads both pkl files using
our load_artifacts() function from utils.py. This happens only once
— so we're not reloading models on every request, which would be
very slow.

The app exposes two endpoints:

  GET / — A simple health check that returns a status OK message.
           Useful for monitoring tools and load balancers to verify
           the service is alive.

  POST /predict — This is the main endpoint. It accepts a JSON
                  body in this specific format:
                  {
                    "customer": {
                      "gender": "Female",
                      "tenure": 12,
                      ...all other fields...
                    }
                  }

Internally, the predict endpoint calls predict_single from utils.py.
This function converts the dictionary into a single-row pandas
DataFrame, applies the transformer, and runs the model's
predict_proba method to get the churn probability.

It returns:
  {
    "churn_prediction": "Yes",
    "churn_probability": 0.83
  }

The churn_prediction is "Yes" or "No" as a human-readable string.

The server runs on port 8000 and is started with:
  python -m app.main

# ═══════════════════════════════════════════════════════════════════
# [SLIDE 10] CODE WALKTHROUGH — batch.py               (~2 minutes)
# ═══════════════════════════════════════════════════════════════════

Now for the batch scoring pipeline.

batch.py is designed to be run as a nightly job — imagine a cron
task that fires every night at 2 AM and scores all active customers.

You run it like this:
  python batch.py --input test_data/all_customers.csv

The --input flag means you can point it at any CSV file — not just
the test file. This makes it completely reusable.

Here's what it does step by step:

1. It reads the input CSV using pandas.
2. For each row, it builds the nested JSON payload that the API
   expects — wrapping the customer fields inside a "customer" key.
3. It sends a POST request to localhost:8000/predict.
4. It collects the churn_prediction and churn_probability from the
   response.
5. If a request fails — due to a connection error, timeout, or a
   non-200 response — it logs the error and moves to the next row.
   It does NOT crash.
6. After processing all rows, it writes scored_customers.csv with
   the predictions for every customer.
7. Finally, it writes a summary to logs/batch_log.txt including:
     - Total requests
     - Successful calls
     - Failed predictions (errors or non-200 responses)
     - Average churn probability

# [SLIDE 12] MONITORING & MAINTENANCE PLAN             (~2.5 minutes)
# ═══════════════════════════════════════════════════════════════════

The final piece of the puzzle is the maintenance plan. A machine
learning model is NOT a one-time artifact. The world changes, and
the model needs to change with it.

I've defined three pillars of maintenance:

PILLAR 1 — RETRAINING

The model should be retrained monthly, or immediately if the
production churn rate deviates by more than plus or minus five
percentage points from the training baseline.

To retrain: you replace the CSV data with fresh labeled data, run
python train.py, and replace the pkl files. Before promoting the
new model, you MUST verify its ROC-AUC meets or exceeds 0.75.
If not, the old model stays in production.

PILLAR 2 — DRIFT DETECTION

Data drift happens when the distribution of incoming data starts
to differ from what the model was trained on. For example, if
customers' average monthly charges shift significantly — the model
may become unreliable.

I recommend monitoring this monthly using Population Stability Index,
or PSI. If any feature has a PSI score above 0.2, it's flagged for
investigation. All incoming API payloads should be logged to a
database so this analysis is possible.

Concept drift — where the relationship between features and churn
changes — is harder to detect. The best approach is to collect
actual churn outcomes after 90 days and compare them to the model's
predictions. If actual churn differs significantly from predicted
churn, it's time to retrain.

PILLAR 3 — VERSIONING

Every model release gets a semantic version number — v1.0.0, v1.1.0,
and so on. Each version is tagged in Git and the pkl files are stored
with version suffixes. This ensures a rollback is always just a
single configuration change.

# [SLIDE 13] KEY LEARNINGS                             (~1.5 minutes)
# ═══════════════════════════════════════════════════════════════════

Working on this project gave me several important learnings.

First — the preprocessing pipeline is just as important as the model
itself. Saving the transformer ensures that inference-time data is
transformed in exactly the same way as training-time data. Without
this consistency, predictions would be meaningless.

Second — packaging the model as an API makes it reusable and
decoupled. The batch script, the web front-end, a mobile app —
any system can consume predictions via a simple HTTP call without
needing to know anything about the underlying ML code.

Third — error handling in production is non-negotiable. The batch
script never crashes on a failed request. It logs the error and
continues. This is the kind of robustness that distinguishes
production code from a Jupyter notebook.

Fourth — model performance is a living metric. An AUC of 0.75 today
doesn't guarantee good performance six months from now. The
maintenance plan I've built ensures the model stays healthy and
relevant as business conditions evolve.
